## 2. Hallazgos

### F-015 — El CONTROL DE CIFRA ADYACENTE publicado en la NOTA DE CIERRE de `S-013` no reproduce
contra el commit de anclaje, por su propia insercion

| Campo | Valor |
|---|---|
| Gravedad | Media |
| Urgencia | No bloqueante |
| Donde | `_audit/S-013.md`, bloque **CONTROL DE CIFRA ADYACENTE — salida:** (dentro de la NOTA DE
CIERRE de la seccion 7) |

- **Que se observo:** el bloque publica una lista de 16 lineas y la prosa que la sigue afirma
  «Ninguna de las dieciseis lineas afirma una cifra que no salga...». Reejecutando la misma orden
  sobre el archivo ya commiteado (`17d769f`, que es el estado final que el propio bloque describe):

  ```
  $ git show 17d769f:_audit/S-013.md > /tmp/s013_head.md
  $ awk '
    /^[[:space:]]*```/ { infence = !infence; if (!infence) { since=0; armed=1 } ; next }
    infence { next }
    armed { since++; if (since<=3 && $0 ~ /[0-9]/ && $0 !~ /^[[:space:]]*$/) print FILENAME":"NR": "$0; if (since>3) armed=0 }
  ' /tmp/s013_head.md | wc -l
  ```
  ```
  18
  ```

  Las dos lineas de mas son: (1) la propia frase de cierre del bloque («... o el total de 13 ordenes
  ancladas»), que quedo dentro de las tres lineas siguientes al cierre de su propio bloque de codigo
  y por tanto se autocaptura; y (2) el desplazamiento de las dos frases ya revisadas de las secciones
  8 y 9 («La tabla ... cuadra con los dos», «Cuatro archivos por promover»), que al insertarse el
  bloque de la CIFRA ADYACENTE (unas 32 lineas nuevas) se corrieron a una linea distinta de la que el
  propio bloque cito como «publicada» — la cifra que citan sigue siendo correcta, pero el numero de
  linea que el bloque anoto (`498`/`499`, `515`/`516`) ya no es el que tienen en el commit final
  (`530`/`531`, `547`/`548`).
- **Por que importa:** el bloque existe exactamente para que una cifra publicada como completa
  («las dieciseis lineas») se pueda contrastar sin rehacer nada. Aqui la cifra de completitud no
  reproduce contra el commit que la contiene: es el mismo defecto que el propio control persigue
  —una cifra tecleada junto a su bloque que no sale de una reejecucion— colandose en el bloque que
  se escribio para impedirlo. No hay ninguna cifra sustantiva falsa (las dos lineas nuevas remiten a
  numeros ya justificados en el propio informe), asi que no cambia ninguna conclusion del cierre.
- **Que lo corregiria:** correr el CONTROL DE CIFRA ADYACENTE **despues** de pegar su propio bloque
  y su parrafo de cierre en el informe, no antes — o, si el orden de escritura no lo permite,
  declarar en la propia nota que el recuento es previo a la insercion del bloque que lo contiene y
  que una segunda pasada sobre el commit final puede devolver un numero mayor por esa causa.
